## P0

### P0-1 `.git` / `.ssh` 写保护可被路径大小写绕过 → 任意代码执行 [实测]

**位置**：`engine/safety/tool_guard.py:91`（`_ALWAYS_BLOCKED`）、`:99`（`_SENSITIVE_DIRS`）

macOS 默认的 APFS 是大小写不敏感、大小写保留。`Path(".GIT/hooks").resolve()`
**不会**把大小写规整成磁盘上真实的 `.git`，而目录分段的安全判定用的是精确匹配：

```python
for part in target.parts:
    if part in self._SENSITIVE_DIRS:   # {".git"} — 精确匹配，无 .lower()
```

同一个函数里第 95 行的 `.env` 检查却用了 `name = target.name.lower()` —— 只有文件名
做了归一化，目录分段没有。这个不对称说明是漏写而非设计取舍。

实测（真实 `FileGuard` + 真实 git 仓库，working_dir 已按生产路径调用
`set_working_directory()` 收窄）：

```
.git/hooks/pre-commit   -> 拦截    'Write inside .git/ is blocked'
.GIT/hooks/pre-commit   -> 放行 ⚠️
.Git/hooks/pre-commit   -> 放行 ⚠️
.ssh/id_rsa             -> 拦截    'Access to .ssh/ is blocked'
.SSH/id_rsa             -> 放行 ⚠️
```

文件系统层同步确认 `.GIT/hooks/pre-commit` 与 `.git/hooks/pre-commit`
`samefile() == True` —— 通过 `.GIT` 写入的内容就落在真实 `.git/hooks/pre-commit` 里。

**完整攻击链**：模型（或经提示注入的内容）调用
`write_file(path=".GIT/hooks/pre-commit", ...)` → guard 放行 → 落盘到真实 git hook →
用户下次 `git commit` 执行任意代码。`.SSH/authorized_keys` 同理。

**修复**：`part in self._SENSITIVE_DIRS` → `part.lower() in ...`，`_ALWAYS_BLOCKED`
同改；`_PLATFORM_DATA_ROOT` / `_MEMORY_WRITE_ROOT` 的 `is_relative_to` 也是大小写敏感
比较，需一并处理。同文件 `.env` 检查已有 `.lower()` 先例。

## P1

### 路由与流程

**P1-1 英文关键词子串误匹配，正常请求被路由到 git 并跳过整个 coding 流水线 [实测]**

`engine/identity/catalog.py:262` 用纯 `in` 子串判断，无单词边界；git 路由
`priority: 30` 为全场最高且 `pipeline: null`；`engine/execution/routing/task_router.py:47`
只要 `score > 0` 就直接返回，不给 LLM 兜底纠偏。三者叠加：

```
输入: Please add a digital signature verification feature to the login flow
  score=3 priority=30 route=git      pipeline=None    命中=['git']   ← "di-git-al"
  score=3 priority=10 route=feature  pipeline=coding  命中=['add']
  => 最终路由: git   pipeline=None

输入: Refactor the legitimate config loader
  score=3 priority=30 route=git      pipeline=None    命中=['git']   ← "le-git-imate"
  score=3 priority=15 route=refactor pipeline=coding  命中=['refactor']
  => 最终路由: git   pipeline=None
```

第二例杀伤力更大：用户明确写了 "Refactor" 并已命中 refactor 路由，仍被 git 抢走。
`pipeline=None` 意味着跳过 understanding→planning→architecture→implementation→validation
全部节点及其门禁，退化成裸 ReAct。同类子串还有 `commit`⊂`commitment`、`fix`⊂`prefix`。
中文输入不受影响（实测中文请求正常进 coding）——**这是一个只伤英文输入的缺陷**。

修复：拉丁字母关键词加 `\b` 单词边界，中文维持子串匹配。

**P1-2 回溯不传递失败原因，纠错机制实际是盲跑**

`engine/execution/pipeline/pipeline.py:231-254`。门禁二次失败触发 switch 回溯时，只
yield `{"from","to"}`，未写 `CTX_RETRY_HINT` / `CTX_RUBRIC_FEEDBACK`，BACKTRACK 事件也
不带 reason（对比 BLOCKED 事件始终带）。目标节点重跑时 messages 仍是最初的原始需求，
模型拿不到"为什么被打回"的任何信号，大概率复现同一份产出。而 `FailureLoopGuard` 按
skill_name 累计、不因回溯重置，第二次失败即 blocked —— 等价于整条流水线只有一次纠错
机会，且这次机会因无信息传递而大概率无效。

### 记忆

**P1-3 中文自然语言查询的 episode 检索恒定返回空 [实测]**

`engine/memory/search.py:135,139`。`stripped.split()` 对中文切不开，整句成为**一个**
term，长度必然 ≥3，因此永远走 FTS MATCH 分支并把整句当作一个短语，要求语料逐字连续
包含这十几个字。实测（sqlite 3.51.0，trigram tokenizer）：

```
语料: 用户上周要求优化数据库查询性能，已通过索引调整解决该问题。
  query="数据库"                          命中
  query="数据库" AND "查询性"               命中
  query="之前数据库查询性能的问题怎么解决的"      空     ← 生产实际输入形态
```

判据反直觉：**输入越长越查不到**。2 字符输入才会落进 `len(term) < 3` 的 LIKE 回退，
那是唯一能工作的路径 —— 而测试
`test_episode_search_falls_back_to_like_for_short_cjk_queries` 测的正是 2 字符，
**恰好选中唯一能过的分支**，掩盖了生产失效。

`engine/execution/orchestration/preparation.py:219` 传入的是 `request.message`
（用户完整消息），所以生产路径 100% 落在失效分支。同一个 query 走
`_select_relevant_durable`（`store.py:149-158`）时反倒做了中文 bigram 切分 ——
**两条检索路径一条做了中文分词，一条没做**。

修复：调 `idx.search` 前对无空格文本做与 `_query_terms` 等价的 n-gram 提取，各 term
分别加引号后 AND 连接。

**P1-4 `compact_episode` 静默覆盖并永久销毁旧 episode**

`engine/memory/compile.py:794`。`atomic_write_text(out, ...)` 无存在性检查、无合并、

**P1-5 `compile_durable` 缺 Dream 式两阶段提交，中断窗口会重复合并同一批证据**

`engine/memory/compile.py:696-730`。`_commit_view` 写完 durable.md 之后才写

`Semaphore`，所有 409 冲突检查只在 **resume** 路径（`184`、`309-331`），普通
`stream_message` 对同一 session 无互斥。因此用户重复提交同一条消息（客户端超时重试 /
未见响应再点一次）时，Run B 会满足全部匹配条件，把仍在运行的 Run A 的半程 checkpoint
当作自己的崩溃恢复点，跳过 node 0 并继承 A 未提交的中间产出，两个 run 并发对同一
working_dir 无协调写入。

缺陷实质：复用 checkpoint 是设计意图（docstring 明确写了 crash recovery），但**无法
区分"上个 run 崩溃了"和"上个 run 还在跑"**。

**P1-7 `sandbox/host.py` 输出排空无超时，后台进程导致 shell 工具永久挂死**

`engine/sandbox/host.py:104-105`。`_drain_streams` 前两层超时各 1 秒，最后一层
`return await drain_task` 无超时。命令派生了 `os.setsid()` 脱离进程组的孙子进程
（"把 dev server 放后台跑"这类极常见用法）时，`os.killpg(proc.pid, ...)` 杀不到它，
它继续持有管道写端，`stream.read()` 永远等不到 EOF。而 shell 工具声明
`concurrency: "serial"`（`agents/tools/shell.py:45`），该 asyncio.Lock 永不释放 ——
此后所有 shell 调用排队卡死，整条 SSE 流不返回。分片 agent 已实测复现。

**P1-8 流式长度截断续写把一条回答拆成多个独立气泡**

`engine/execution/react/react_loop.py:538-539,723-729`。续写分支只

**P1-9 `render_ui` 超大 JSON 整数触发未捕获 `OverflowError`，整轮任务硬失败**

## P2

**P2-1 Anthropic 流内 error 事件不触发重试** — `anthropic.py:219-224`。
`overloaded_error`（文档明确标注瞬时可重试）在流中途以协议内事件上报时，

仅解析入口（面对 provider 实时返回）成立，单轮失败可重试。
