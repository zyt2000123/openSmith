## P1

### [P1] `package.json` — ink 降级到 6.8.0 重新引入 ink#901：粘贴任何含 ANSI 颜色码的文本使整个进程崩溃

未提交改动把 `ink` 从 `^7.1.0` 改为 `^6.8.0`（同时移除 `ink-text-input`，由自研 `composer.tsx` 替代）。ink 6.8 的 `parse-keypress.js` 把 `\x1b[0m` 一类 SGR 序列解析为 `ctrl=true, name=undefined`，`use-input.js:90` 取 `input = keypress.name`（undefined），`:101` 调 `input.startsWith(…)` → TypeError。ink 7.1 该处已改为 `input = keypress.name ?? ''`，注释直接引用 "crashes entire Ink app (see ink#901)"。

**失败场景**：用户把带颜色的报错日志/`ls --color` 输出粘给 Agent（核心用例）——粘贴内容含 `\x1b[0m`（几乎所有彩色输出都有）→ 进程 TypeError 退出（exit 1），Ink 退出清理不执行，终端可能残留 raw mode。`grep uncaughtException shell/src shell/bin` 零匹配，无兜底。

**实测**：`parseKeypress('\x1b[0m')` → `ctrl=true, name=undefined`；`'\x1b[31m'`、`'\x1b[1;32m'` 同。PTY 端到端喂入含该序列的文本 → `TypeError: Cannot read properties of undefined (reading 'startsWith') at use-input.js:101`，exit=1。`useShellInput` 常驻 active，故 shell 运行期间恒可触发。

**修复方向**：不能直接回退 ink 7——`@json-render/ink` 最新版（0.19.0）peer 仍是 `ink: ^6.0.0`。可选项：① npm `overrides` 强升 ink 7 并回归验证 `@json-render/ink` 是否真的不兼容；② 保留 ink 6 并对 `process.stdin` 做一层包装，在数据进 ink 前剥离 ESC 序列（同时也解决 P2 的 `\r` 污染）；③ 放弃 `@json-render/ink`（它只服务 smith-ui 结构化渲染）。**confidence: high**

### [P1] `transcript-state.ts:323-330` — `done` 不收敛任何未终结块，多条服务端合法序列使 skill/tool 块永久停在"运行中"并烧进 `<Static>` 滚回区

`closeLatestTurn` 只做三件事：终结 thinking、清 provisional、置 `streaming:false`；running 态的 skill/tool 块原样保留。紧邻的 `interruptLatestTurn`（`:332`）才有收敛逻辑——收敛原语已存在，只是 `done` 路径不用它。

**同根残留**：`activity.ts` 对 `done` 不做清理，悬空 tool 留在 `running` 映射；`hud.tsx:220-222` 渲染 running 不检查 busy，且 toolActivity 同会话内不按轮重置 → 失败 run 之后所有后续轮次 HUD 都挂着假的 ◐ 运行指示。

**修复方向**：`done` 分支改用 `interruptLatestTurn`（按 `status` 决定 outcome），或让 `closeLatestTurn` 也收敛 running 块；同时在 done 时清 `activity.running`。**confidence: high**

### [P1] `index.tsx:1042-1051`（及所有 `transcriptEpoch` bump 点）— epoch 重挂与 Ink `fullStaticOutput` 缓存叠加，动态区超过终端高度时历史成倍重印，`/clear` 掉的内容会回魂

Ink 把每次 static 输出**只增不清**地累积（`ink.js:173` 是构造函数里唯一一次置空，`:257`/`:316` 都是 `+=`），并在 `lastOutputHeight >= stdout.rows` 时执行 `stdout.write(clearTerminal + fullStaticOutput + output)`（`:327`）——清屏后重印**累积的全部** static。而 shell 的 `clearTerminal()`（`term.ts:7`）只清终端，清不掉 Ink 进程内的这份缓存；epoch bump 使 `<Static key={transcript-N}>` 重挂、渲染索引归零，于是同一批 entry 被再次写入缓存。

**失败场景**：聊若干轮 → 任一次 epoch bump（Ctrl+O 切视图、`/clear`、`/new`、`/resume`、进出 `/tokens`·`/runs`、转录超 200 条触发 trim）→ 之后 Smith 输出一个长回答，动态区高度 ≥ 终端行数（24 行终端一个长回答即达）→ 屏幕与滚回区出现 2 份完整历史，每多一次 bump 多一份；`/clear` 之后旧会话内容同样回魂。busy 期间 `RunProgress` 每秒重渲染，高度超限时等于每秒重印 N 份。

**修复方向**：epoch bump 时重建 Ink 实例（unmount + 重新 render，使 `fullStaticOutput` 归零），或不以 remount 方式替换 `<Static>` 内容。**confidence: high**（ink 源码链路 + 实验复现：假 TTY rows=10，remount 后撑到 12 行，itemA/itemB 各出现 2 次）

### [P1] `index.tsx:1165` + `input.ts:250-270` — tokens/runs 全屏面板期间审批到达：UI 完全不可见但按键仍被审批处理器消费，Enter 盲批 shell 命令、Esc 静默杀 run

`{panel !== "tokens" && panel !== "runs" ? <ShellFooter/> : null}` 使 `ApprovalPrompt` 与 statusLine 整体不渲染，而两个面板自身不显示任何审批信息（grep `approval|statusLine` 于 token-panel/run-panel 零匹配）；`store.ts` 的 `approval_required` 分支不切 panel。`routeInput`（`input.ts:418-434`）把 `handleApprovalInput` 排在所有 panel handler 之前，`pendingApproval` 非空即消费 Tab/箭头/Esc/Enter，与 panel 无关。

**失败场景**：Agent 后台运行时用户进 `/token` 看用量 → engine 请求工具审批 → 屏幕上毫无提示 → 用户按 Esc（返回面板的肌肉记忆）→ `cancelRequest()` 静默取消正在运行的任务；按 Enter → `resolveApproval(approvalIndex === 0)`，默认 0 = "Allow once" → **在完全不知情的情况下批准了一条 shell 命令**；Tab/方向键被吞 → 锁在面板里出不去。

**修复方向**：`approval_required` 到达时若处于全屏面板则强制切回 chat（或在两个面板内渲染审批条）；并给 `handleApprovalInput` 加 panel 守卫。**confidence: high**

### [P2] `transcript-state.ts:354`/`:327` 对撞 `session_service.py:663-680` — 取消/失败时 shell 抹掉屏幕上的草稿文本，server 却把同一段文本落库，live 视图与会话真实内容分叉

`interruptLatestTurn`/`closeLatestTurn` 均置 `provisional: []`，已渲染的 "draft…" 文本从屏幕消失，定格后的 turn 里没有任何 assistant 文本。但 server 生成器在 finally 里执行相反决策（注释原话 "On disconnect preserve exactly that visible state"）：`reply_text = visible_provisional_reply` 落库为 assistant 消息。后果：用户以为这轮无产出；下一条消息的模型 history 里有一段用户从没见过的回复；`/resume` 或重启后该文本凭空出现。**修复方向**：取消/失败时把 provisional 定格为普通 assistant 文本（与 server 落库一致），而非清空。**confidence: high**

### [P2] 全渲染路径 — 不可信文本中的 OSC 转义序列穿透到终端（含 OSC 52 写系统剪贴板）【安全】

`shell/src` 内零 ANSI 净化（唯一转义序列是 `term.ts` 自己的清屏）。实测：`<Text>` 原始路径、`stripEmojiIcons()` 之后（assistant 文本路径）、`truncateDisplay()` 之后（工具提示/审批路径）三条路径上，`\x1b]52;c;<base64>\x07`（写剪贴板）与 `\x1b]7;`（伪造 cwd）均完整到达 stdout；CSI 类（`\x1b[2J`、`\x1b[1;1H`）被 Ink 的换行逻辑消化，OSC 类不被。

**失败场景**：工具结果来自任意命令输出/文件读取/网页抓取——`cat` 一个精心构造的文件、或抓一个含 OSC 52 的页面 → 用户剪贴板被静默替换（经典链路：替换掉用户刚复制的命令或地址，用户粘贴即执行）。OSC 52 写入在 kitty/wezterm/alacritty 默认允许、iTerm2 可配、tmux 需 `set-clipboard on`、xterm 需 `allowWindowOps`；即使剪贴板被禁，OSC 0/7/8 的标题伪造、cwd 伪造、超链接钓鱼在所有终端可用。**修复方向**：渲染前对不可信文本剥离 C0/C1 控制字符与 ESC 序列（一个函数，同时也修 `\r` 污染）。**confidence: high**

### [P2] `window-size.ts:21-28` × `transcript.tsx:641` — 每条转录 entry 各注册一个 stdout resize listener，≥9 条即把 `MaxListenersExceededWarning` 打进渲染区

未提交改动因 ink 6.8 无 `useWindowSize` 导出而新建本地 hook（必要修复），但它被 `TranscriptEntryView` 每条 entry 调用一次，每实例 `stdout.on("resize", …)`、无共享无 `setMaxListeners`。Static 全量挂载（恢复 ≥10 条会话、或任一次 epoch remount）时 React 先 flush 全部挂载 effect 再卸载清理 → 第 11 个 listener 触发 Node 警告写 stderr，直接砸进 Ink 渲染区（转录上限 200 条，峰值可到 200+ listeners）。**修复方向**：模块级单例订阅共享 size；或用 `TranscriptEntryView` 已有的 `terminalColumns` prop 由顶层注入。**confidence: high**（实验复现）

### [P2] `token-panel.tsx:162-181`/`:183-199` — `/tokens` 的 Overview 与 Models 两个 tab 不看终端宽度，窄终端逐行交错折行

### [P2] `composer.tsx:91-106` — 受控 value 回流 + ink 同 chunk 多 event 同步派发 → 过期闭包丢输入

ink 的 `App.js handleReadable` 用 `while` 同步循环逐 event `emitInput`，而 `useInput` 的 listener 重注册发生在 React passive effect（异步）——同一 chunk 内第 2 个及以后的 event 拿到的还是旧渲染闭包（`value`/`cursor` 过期），后一段基于旧值计算并覆盖前一段。`input-parser.js` 按 ESC 序列边界拆分，故 `"abc\x1b[Adef"`（混合序列、高延迟 SSH 合包、含 ESC 的粘贴）拆成 3 个 event。PTY 实测：输入框最终只剩 `"def"`，`"abc"` 静默丢失，三个 event 的闭包 value 全是旧值。纯文本粘贴合并为单 event，日常打字/中文 IME 不受影响。**修复方向**：用 ref 持有最新 value/cursor，或改为非受控本地状态 + 单向上报。**confidence: high**

### [P2] `composer.tsx:45-64` — 多行/含控制字符粘贴：`\r`、`\t` 原样插入 value，输入框渲染成逐字符竖排，提交消息被污染

终端把粘贴的 `\n` 转成 `\r` 发送；ink 6.8 无 bracketed paste 支持（grep `200~|paste|bracketed` 零匹配）。`"line1\rline2"` 作为单 event、`key.return=false`、name=`''` → `applyComposerEdit` 把 `\r` 当普通字素插入。PTY 实测输入 `"AAA\rBB"` 后输入框渲染成每字符一行的竖条，布局完全破坏；提交时 `submitChat` 只 `trim()` 首尾，中间 `\r` 原样进入发给服务端的 payload。`\t`、`\x07` 同样字面插入。旧 `ink-text-input` 也不过滤（非行为回归），但自研替换时应补上这道防线。**修复方向**：`applyComposerEdit` 插入前过滤控制字符（`\r`/`\n` 转空格或忽略）。**confidence: high**

### [P2] `input.ts:351-382` + `index.tsx:1052-1065` — 历史导航：浏览中编辑后回到底部，用陈旧 `historyDraft` 覆盖并静默丢弃刚输入的内容

## 未计入缺陷的结构性观察

- **双 `useInput` 消费者顺序会翻转**：初始 routeInput → Composer，任一次共同重渲染后 passive effect 子先父后重注册，变为 Composer → routeInput。当前所有按键两个方向均幂等或互斥，无用户可观测差异，但这是隐性契约——任一方对同一键新增非幂等处理即双触发。

- **`bridge.ts:377-380` `refreshSkills()`** 全仓无调用者，且是唯一无错误处理的 bridge 方法。预先存在的孤儿代码。
- **HUD 私有宽度逻辑**与 `string-width` 对拍：仅旗帜（🇨🇳）与 keycap（1️⃣）低估 1 列，HUD 内容出现概率极低。

- **`send_message` 重复落库（历史疑点）已排除**：user 与 assistant 各只落库一次，resume 前先 `discard_assistant_messages_after_user` 去重，测试锁定。
