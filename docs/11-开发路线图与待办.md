## P0 · 可靠性与安全闭环

1. **持续修复审计发现并维护回归测试**：以 Shell 审计和正式测试为输入；对每个修复记录实际验证命令与剩余风险。
2. **明确 Run 终态与恢复语义**：覆盖 provider 中断、审批超时、客户端断连、服务重启与重复提交，确保转录、SQLite 消息、checkpoint 与 RunState 不分叉。
3. **持续扩大 Shell 净化与窄终端覆盖面**：解码边界净化已落地（`shell/src/sanitize.ts`，覆盖 OSC 52/7/0/8 的剪贴板写入、cwd/标题伪造与链接隐藏威胁模型），显示宽度与窄终端布局由 `text-layout.ts`/`window-size.ts` 承担；剩余工作是把粘贴控制字符、窄终端布局和审批可见性的覆盖面持续扩大，作为安全/正确性问题处理，不仅是 UI 优化。
4. **可观测性保留策略**：为 trace、incident、run summary 与 token 统计定义保留期、容量、清理任务与故障降级语义。

## P1 · 单 Agent 体验完善

1. **真实模型端到端门禁**：除 mock/unit test 外，建立不泄露凭据的 opt-in provider smoke test，覆盖流式、工具调用、长度终态与配置错误。
2. **文档-代码一致性检查**：将路由表、Shell 命令、identity/pipeline 名称和 Markdown 链接纳入 pre-push 钩子或轻量 CI（仓库明确不设 CI，`.githooks/pre-push` 是当前唯一自动触发点）；阻止删除模块后文档继续宣称能力存在。
3. **MCP 运行体验**：完善配置诊断、连接/重连、工具冲突信息、请求超时和 session pool 的可见状态；维持与本地 tool 相同的安全链。
4. **技能交付质量**：为 shipped skills 规定输入、产物、验收命令和 gate 的最小契约，避免只有提示词没有可验证闭环。
5. **自动任务运行契约**：明确后台 Run 的并发、取消、资源回收、权限和人工审批交互，尤其不能让后台任务隐式获得前台授权。

## 进入开发前的 Definition of Ready

任一待办进入实现前，至少要写清：

1. 用户结果、非目标和验收条件；
2. 所属层与接口（事件/API/schema/文件格式）；
3. 权限、副作用、失败与恢复语义；
4. 数据迁移、兼容与回滚方案；
5. 最小回归测试和需同步的当前实现文档。

做出跨模块且难回滚的决定时，先在 `docs/adr/` 新建 ADR。调研得出的建议先留在 `research/`，未通过上述准备条件前不进入产品能力表。
