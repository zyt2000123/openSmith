## 0. 最容易搞混的九组

先把最常被弄反的概念摆出来。

```mermaid
flowchart TD
    subgraph 一["Agent vs Identity"]
        A1["Agent：唯一运行实体<br/>只有一个 Smith"] -.->|"不是"| A2["Identity：能力档案<br/>可以有多个"]
    end
    subgraph 二["Route vs Pipeline"]
        B1["Route：意图声明<br/>可以没有 pipeline"] -.->|"不是"| B2["Pipeline：技能链<br/>被 route 引用"]
    end
    subgraph 三["Gate vs Guard"]
        C1["Gate：产出契约检查<br/>不过则重试"] -.->|"不是"| C2["Guard：安全边界<br/>不过则拒绝"]
    end
    subgraph 四["Session vs Run"]
        D1["Session：一串消息"] -.->|"不是"| D2["Run：一次执行"]
    end
    subgraph 五["Skill vs Tool"]
        E1["Skill：做事的方法论<br/>Markdown"] -.->|"不是"| E2["Tool：能力<br/>Python 函数"]
    end
```

| # | 容易混的一对 | 关键区别 |
|---|---|---|
| 1 | **Agent** vs **Identity** | Agent 只有一个（Smith）；Identity 是能力档案，可以有多个，切换 identity **不创建新 Agent** |
| 2 | **Route** vs **Pipeline** | Route 是意图声明（可以 `pipeline: null`）；Pipeline 是被引用的技能链 |
| 3 | **Gate** vs **Guard** | Gate 检查产出契约，不过就带反馈重试；Guard 检查安全，不过就拒绝 |
| 4 | **Session** vs **Run** | 一个 Session 有多个 Run；Run 才有状态机和 trace |
| 5 | **Skill** vs **Tool** | Skill 是"怎么做"（Markdown）；Tool 是"能做什么"（Python） |
| 6 | **FactGate** vs **ToolGuard** | FactGate 只挑战可重试可关闭；ToolGuard 不可绕过 |
| 7 | **trace** vs **summary** | trace 是逐事件原始记录；summary 是聚合投影 |
| 8 | **context.md** vs **durable.md** | 前者是用户协作偏好；后者是项目工作记忆 |
| 9 | **`recent.jsonl`** vs 记忆视图 | 前者是候选证据日志；后者是编译产物 |

## 1. 核心概念

### Agent

Smith 本身。**运行时唯一实体**，一个进程只有一个。有一份档案（`agent_profiles` 表 + `~/.agent-smith/agent/`）。

产品语言禁令：不说 "sub-agent"、"employee"、"digital employee"、"hire"。

- 代码锚点：`server/app/services/agent_profile_service.py`
- 详见：[01 · 总览](../guide/01-产品定位.md) §3.2

### Identity（身份）

一份**能力档案**：角色提示 + 工具白名单 + 技能白名单 + 路由声明。目前两个：`smith`（默认）、`coding`。

`catalog.py` 的 docstring：

> 一个身份是唯一常驻 Smith agent 的一份能力档案。**它不是一个单独运行的 agent**，也从不拥有单独的服务端档案记录。

- 代码锚点：`agents/identities/*.yaml`、`engine/identity/catalog.py:IdentitySpec`
- schema：`agentsmith.identity/v1`
- 详见：[08 · Agents 内容层](../layers/42-Agents.md) §3

### Route（路由）

身份内声明的一条意图：`id` / `keywords` / `examples` / `pipeline` / `priority`。

**`pipeline` 可以是 `null`**——`smith` 身份的 `git` 路由就是这样，它选中身份的工具和安全检查，但不进多步工作流。

评分：examples 命中 +10，keywords 命中 +3。排序键 `(score, priority, -声明顺序)`。

- 代码锚点：`engine/identity/catalog.py:RouteSpec` / `_score()`
- 详见：[08 · Agents 内容层](../layers/42-Agents.md) §3.4

### RouteDecision

路由的完整结果：`identity` + `route_id` + `pipeline_id` + `score`。未命中任何路由时是 `RouteDecision(default, "direct", None)`。

- 代码锚点：`engine/identity/catalog.py:RouteDecision`

### Pipeline（管线）

一条声明式技能链。三条：`requirements-research`、`tdd-development`、`code-review`。

每个 step 有 `skill` / `gate` / `condition` / `allowed_tools` / `instructions` / `await_user_input_marker`。

- 代码锚点：`agents/pipelines/*.yaml`、`engine/execution/pipeline/pipeline.py`
- 详见：[02 · 快速上手](../guide/02-快速上手.md) §14

### SkillChain

管线被解析后的运行时对象。节点数、门禁、条件都在这里。

- 代码锚点：`engine/execution/pipeline/skill_chain.py:SkillChain`

### Gate（门禁）

节点产出的**契约检查**。三态：`pass` / `retry` / `fail`。

- `retry` → 带 `retry_hint` 重跑本节点
- `fail` → 交给 `FailureLoopGuard`

20 个门禁：通用 5 个 + 编码 15 个。

- 代码锚点：`engine/execution/pipeline/gate.py:GateResult`、`agents/gates/*/gates.py`
- 详见：[04 · Engine 核心执行](../subsystems/20-Agent-Loop.md) §6.2

### LLMGate

两层门禁：**便宜的启发式预过滤 + LLM 语义验证**。输入上限 2000 字符，**两端各留一半**。

- 代码锚点：`engine/execution/pipeline/gate.py:LLMGate` / `_bounded_gate_output`
- 详见：[04 · Engine 核心执行](../subsystems/20-Agent-Loop.md) §6.3

### Condition（条件）

管线节点的执行条件。目前只有一个：`coding_bugfix_needs_diagnosis`。

- 代码锚点：`agents/conditions/coding.py:CONDITIONS`

### Skill（技能）

一个含**顶层 `SKILL.md`** 的目录，描述某类任务的工作方法。16 个（24 个目录里）。

- 代码锚点：`agents/skills/*/SKILL.md`、`engine/skill/registry.py`
- 详见：[08 · Agents 内容层](../layers/42-Agents.md) §5

### Tool（工具）

一个定义了 **`TOOL_META` + `execute`** 的 Python 模块。19 个。没有基类、没有装饰器。

- 代码锚点：`agents/tools/*.py`、`engine/tool/registry.py`、`engine/tool/interface.py:ToolDefinition`
- 详见：[08 · Agents 内容层](../layers/42-Agents.md) §4

### Hook（钩子）

工具生命周期三段：

| 类型 | 能阻断 | 能异步 | 返回 |
|---|---|---|---|
| `PreToolHook` | ✅ | ❌ | `(allowed, denial_reason)` |
| `PostToolHook` | ❌ | ✅ | `list[str]` 警告 |
| `StopHook` | ❌ | ✅ | — |

4 个内建：`config-protection`、`console-warn`、`quality-gate`、`cost-tracker`。

- 代码锚点：`engine/execution/hooks/tool/interface.py`、`agents/smith/hooks/`
- 详见：[08 · Agents 内容层](../layers/42-Agents.md) §7

### Run（运行）

一次任务执行。有 `run_id`、7 态状态机、trace、summary，可中断可恢复。

状态：`QUEUED` / `RUNNING` / `WAITING_APPROVAL` / `COMPLETED` / `INCOMPLETE` / `FAILED` / `CANCELLED`。

- 代码锚点：`engine/execution/orchestration/run_state.py:RunStatus`
- 详见：[03 · 架构总览](10-系统架构.md) §4

### Session（会话）

一串消息 + 上下文摘要 + 模型档案绑定。**一个 Session 包含多个 Run。**

- 代码锚点：`sessions` 表、`server/app/services/session_service.py`

## 2. 记忆

### Memory（记忆）

两份渲染视图，**整份注入 prompt**：

| 视图 | 路径 | 作用域 | 预算 | 章节 |
|---|---|---|---|---|
| `context.md` | `agent/context.md` | user | 4000 字符 | Confirmed Preferences / Collaboration Patterns / Stable User Context |
| `durable.md` | `agent/memory/durable.md` | project | 10000 字符 | Active Work / Pending / Verified Outcomes / Decisions / Known Pitfalls |

**没有 embedding、没有 FTS、没有 episodes、没有查询时检索。**

- 代码锚点：`engine/memory/MEMORY_POLICY.md` frontmatter
- 详见：[05 · 记忆系统](../subsystems/21-记忆系统.md)

### `recent.jsonl`（证据日志）

**候选证据**的事件日志。不是记忆——写进去只表示"候选证据已记录"。保留窗口 7 天。

- 代码锚点：`engine/memory/store.py`

### ChangeSet（变更集）

记忆编译器的输出单位。**不是文档，是一组带证据的变更**（`add` / `remove` / `replace`）。

每条变更必须带 `evidence.ref`（真实事件时间戳）和 `evidence.quote`（原文片段）。

- 代码锚点：`engine/memory/_changeset.py:MemoryChange`
- 详见：[05 · 记忆系统](../subsystems/21-记忆系统.md) §6

### 三道守卫（Adjudication）

代码在 Reviewer 之前**逐条**裁决变更：

| 守卫 | 问题 |
|---|---|
| **溯源**（Traceability） | 被引用的证据存在吗？新内容留在它之内吗？ |
| **保留**（Retention） | 这条 bullet 到底可不可以被删？ |
| **落位**（Placement） | 这个章节允许承载这种强度的断言吗？ |

10 个拒绝码。

- 代码锚点：`engine/memory/_guards.py:adjudicate()`
- 详见：[05 · 记忆系统](../subsystems/21-记忆系统.md) §7

### 可证伪锚点（Falsifiable anchor）

内容里能被机械核对的片段：URL、反引号内容、带扩展名的路径（可带 `:行号`）、6 位以上数字。

**散文式表述没有锚点，交给 Reviewer。**

- 代码锚点：`engine/memory/_guards.py:_ANCHOR_PATTERNS`

### Dream

低频记忆卫生作业，每 50 次触发一次。**不产生新知识，也不改写记忆内容**：清洗密钥与注入，回收 `recent.jsonl` 的过期前缀。

- 代码锚点：`engine/memory/dream.py:run_dream()`
- 详见：[05 · 记忆系统](../subsystems/21-记忆系统.md) §10

### Cleanup journal

`.dream_cleanup.json`。Dream 替换日志文件**之前**必须先写它（旧/新哈希 + 两个 offset），否则崩溃会让游标指过已下移的证据、静默跳过。

- 代码锚点：`engine/memory/dream.py:DreamCleanup`

### 编译游标

每个视图**各有一个**：`.compile_offset`（durable）、`.compile_offset_context`（context）。只推进到"本次真的送进 prompt 的那一条"。

- 详见：[05 · 记忆系统](../subsystems/21-记忆系统.md) §9.3

### 四种编译终态

| 终态 | 含义 | 计入跳过计数 |
|---|---|---|
| `written` | 有变更写入 | — |
| `deferred` | 没有任何可应用变更 | **是**（连续 3 次则 `skipped`） |
| `rejected` | 草稿不安全或结构不合法 | 否 |
| `failed` | 供应商故障、超时、密钥失效 | 否 |

- 详见：[05 · 记忆系统](../subsystems/21-记忆系统.md) §9.1

## 3. 执行

### ReAct 循环

核心执行循环：模型响应 → 工具调用 → 结果 → 下一轮，全在一条历史里。

预算：60 次有效迭代、20 次失败恢复、20 次事实门挑战、2 次假最终回答修复、2 次长度续写。

- 代码锚点：`engine/execution/react/react_loop.py:react_event_loop()`
- 详见：[04 · Engine 核心执行](../subsystems/20-Agent-Loop.md) §4

### ExecutionEvent

引擎产出的事件。**27 种**类型。`data` 是 `dict[str, Any]`。

- 代码锚点：`engine/execution/events.py:EventType`
- 详见：[03 · 架构总览](10-系统架构.md) §3

### Provisional（试探性输出）

管线场景特有：节点输出**先流式渲染**，门禁不过要重跑时**从界面上撤回**。

三个事件：`PROVISIONAL_TEXT_DELTA` / `PROVISIONAL_COMMIT` / `PROVISIONAL_RETRACT`。

- 详见：[03 · 架构总览](10-系统架构.md) §3.2、[11 · Shell 终端 UI](../layers/44-Shell.md) §5.3

### 假最终回答（Incomplete final）

模型调完工具后说一句"让我再查一下 X"就停了——这不是最终回答，是没兑现的承诺。用正则识别（长度上限 240 字符）。

- 代码锚点：`engine/execution/react/budget.py:looks_like_incomplete_final_after_tool()`

### PromptLayer

system prompt 的一层。16 层，每层带五个正交维度：`source` / `authority` / `trust` / `scope` / `load_reason`，外加 `trim_priority`。

- 代码锚点：`engine/context/assembler.py:PromptLayer`
- 详见：[04 · Engine 核心执行](../subsystems/20-Agent-Loop.md) §2

### 稳定前缀（Stable prefix）

从第 1 层开始**连续**、跨请求不变的那一段层。当前是第 1–10 层（第 11 层 `eval_guidance` 是易变的）。

**必须连续**，因为 provider 的 prompt 缓存按**字节前缀**匹配。

- 代码锚点：`engine/context/assembler.py:_stable_prefix()`

### `trim_priority`

层的裁剪优先级，**数字越小越先被裁**。`None` 表示永不裁剪（16 层里有 10 层是 `None`）。

裁剪顺序：`output_style`(10) → `durable_context`(19) → `skills`(30) → `tool_definitions`(35) → `toolbox_policy`(40) → `style`(50)。

### PromptManifest

一次装配的**脱敏收据**，可安全存进 trace：层名、来源、token 数、哈希，**不含内容**。

- 代码锚点：`engine/context/assembler.py:PromptManifest`

### 检查点（Checkpoint）

会话级的管线恢复点。两种恢复语义：

| 情形 | 从哪个节点继续 | 用户消息怎么用 |
|---|---|---|
| `awaiting_user_input` | **同一个**节点 | 作为 `user_response` |
| 崩溃恢复 | **下一个**节点 | 必须与原始请求逐字一致 |

- 代码锚点：`engine/execution/orchestration/agent_loop.py:_apply_session_checkpoint()`
- 详见：[03 · 架构总览](10-系统架构.md) §6

### `FailureLoopGuard`

节点级失败升级：`retry`（第 1 次）→ `switch`（第 2 次）→ `blocked`（第 3 次）。**按 `error_type` 作键**，不按输出哈希（LLM 输出每次都变，永远不收敛）。

- 代码锚点：`engine/execution/pipeline/backtrack.py`

### `RuntimeContext` / `RuntimeServices` / `EngineRequest` / `EngineResult`

Engine 对外的四个数据契约（加 `ExecutionEvent` 共五个）。

- 代码锚点：`engine/execution/orchestration/runtime.py`
- 详见：[03 · 架构总览](10-系统架构.md) §2

## 4. 安全

### ToolGuard

**不可绕过**的安全边界。1365 行。拦：路径攻击、31 条危险命令规则、平台完整性、敏感读。

- 代码锚点：`engine/safety/tool_guard.py`
- 详见：[06 · 安全与安全边界](../subsystems/23-工具与安全.md) §3

### FactGate（事实门）

**只挑战不阻断**的行为纠偏：第一次编辑前必须先做只读调查。可用 `AGENT_SMITH_FACT_GATE` 关闭。

**必须排在 ToolGuard 之后**——有测试强制这个顺序。

- 代码锚点：`engine/safety/fact_gate.py`
- 详见：[06 · 安全与安全边界](../subsystems/23-工具与安全.md) §7

### ToolPolicy

把 ToolGuard 和 FactGate 适配成同一个 `PolicyChecker` 协议，按顺序跑，第一个阻断者获胜。

**例外**：需要审批的决定被**延迟**，先跑完后面的检查器——因为"先去调查"优先于"打扰用户审批"。

- 代码锚点：`engine/safety/tool_policy.py:ToolPolicy.evaluate()`

### PermissionLevel

`read` → `write` → `execute` → `destructive`。策略链沿途取最高。

### RiskTier

`ROUTINE`(0) → `ELEVATED`(1) → `HIGH`(2) → `CRITICAL`(3)。

**决定缓存策略**：只有 `ELEVATED` 及以下能进会话白名单；`HIGH`/`CRITICAL` 每次重新授予。

- 代码锚点：`engine/safety/risk.py`

### ApprovalScope

用户看到并批准的**一次性能力**：`host_command` / `path` / `network` / `operation`。会被 `ToolRegistry` **再检查一遍**。

- 代码锚点：`engine/safety/approval.py:ApprovalScope`

### ApprovalBroker

审批的等待与解析。超时 300 秒。

- 代码锚点：`engine/safety/approval.py:ApprovalBroker`

### `boundary_block`

`GuardResult` 的一个字段：**唯一的问题是工作目录边界**。会话白名单可以放宽它，但高风险审批仍然可见。

### `declared_paths`

调用方**写的**路径拼法（绝对化但**不解析**）。因为 `resolve()` 会抹掉符号链接的名字，而守卫的目录成分规则按名字匹配。

**不进调用指纹**——它派生自 `arguments`。

- 代码锚点：`engine/tool/interface.py:ToolCall.declared_paths`

### 不可委派写根（Non-delegable write root）

Agent **不能写**的平台目录（`~/.agent-smith`），只有记忆目录下三个文件例外。

- 代码锚点：`engine/safety/tool_guard.py:_PLATFORM_DATA_ROOT`

### EvalGuard（评测敏感）

检测"这可能是一次评测/跑分"，注入一段禁止作弊的指引（prompt 第 11 层）。

- 代码锚点：`engine/safety/eval_guard.py`

### Seatbelt

macOS 的 `sandbox-exec` 沙箱。环境变量白名单只有 5 个。

**注意**：`engine/` 的 ~59 个跳过测试几乎全是 Seatbelt 测试，每个都带 `@pytest.mark.skipif(sys.platform != "darwin")`。

- 代码锚点：`engine/sandbox/macos_seatbelt.py`

### 审计哈希链（Hash chain）

防篡改追加日志：每条记录带 `seq` / `prev_hash` / `hash`。

**它做的是检测，不是防御**——能编辑日志的人同样能重写链条和锚点。

- 代码锚点：`common/hash_chain.py`
- 详见：[06 · 安全与安全边界](../subsystems/23-工具与安全.md) §10

## 5. LLM

### LLMPort

**执行层唯一认识的模型接口**。实现者：`ProviderClient`、`RecordingLLM`、`ReplayLLM`、测试替身。

- 代码锚点：`engine/llm/port.py`

### ProviderAdapter

私有的适配器接缝，**只有 `ProviderClient` 消费**。实现者：`OpenAIAdapter`、`AnthropicAdapter`。

- 代码锚点：`engine/llm/adapters/base.py`

### LLMUsage（用途路由）

三条：`INTERACTIVE`（主对话）、`GATE`（门禁判定）、`BACKGROUND`（记忆编译、自动任务）。各有独立的模型配置与超时档。

- 代码锚点：`engine/llm/model_config.py:LLMUsage`

### 五层配置合并

环境变量 → 平台 `~/.agent-smith/config.yaml` → Smith 种子 `agents/smith/config.yaml` → Smith 运行时 `~/.agent-smith/agent/config.yaml` → 会话覆盖。**下层覆盖上层。**

`None` 表示"不表态"，不覆盖下层。

- 代码锚点：`engine/llm/model_config.py:resolve_llm_config()`
- 详见：[02 · 快速上手](../guide/02-快速上手.md) §3.1

### `*_declared`

`ModelLimits` 上的布尔字段：区分"模型声明了这个值"和"没声明所以我用了默认值"。

同类设计：`usage.py` 的 `usage_reported`、`health.py` 的 `tool_success_rate=None`。

### `prefix_cache_key`

传给 provider 的缓存提示。**默认能力为 `False`**——只有声明支持的 adapter 才会收到它。

绑定的是**裁剪之后实际渲染**的稳定前缀。

### GenerationRecord

每次模型调用一条记账记录：`purpose` / `usage` / `ttft_ms` / `total_ms` / `stream` / `ok` / `source_key`。

**记录严格尽力而为**：sink 失败绝不影响模型调用。

- 代码锚点：`engine/llm/observability.py`

### `vendor`

供应商**显示名**。只能写在顶层，不进路由覆盖，不进 adapter 请求，但会进运行时 prompt 元数据（让"你是什么模型"有诚实答案）。

**算客户端缓存指纹时被显式剔除。**

## 6. 可观测

### trace

一次 run 的**逐事件 JSONL**，带哈希链。两层脱敏（按键名 + 按值内容）、有界（4096 字符 / 4 层 / 100 项）。

- 代码锚点：`engine/observability/trace_store.py`

### summary

一次 run 的**聚合投影**：事件计数、工具调用数、回退数、token 用量、终态。**不保留原始载荷。**

- 代码锚点：`engine/observability/projections.py:RunSummary`

### Incident（事故）

确定性分类的运行失败：`budget_exhausted` / `tool_timeout` / `repeated_backtracks` / `run_failed` / `trace_integrity`。每个带 `evidence`。

- 代码锚点：`engine/observability/incidents.py:RunIncident`

### Diagnosis（诊断）

根因分析。取**最具体**的事故作主因（优先级 `tool_timeout` 0 < `budget_exhausted` 1 < `run_failed` 2）。

**提议变更但从不应用。**

- 代码锚点：`engine/observability/diagnosis.py:RunDiagnosis`

### ImprovementProposal（改进建议）

由诊断产出的保守建议，**永远需要审批**。`trace_integrity` 类不产出建议（trace 被动过时任何结论都不可信）。

**优先建议行为改动而非放宽参数**：预算耗尽的建议是"减少重复调用"而不是"调高上限"。

- 代码锚点：`engine/observability/proposals.py`

### AgentHealth（健康度）

运行窗口的聚合指标。工具成功率**排除三类**：门禁探针、被拒审批、超时审批。

没有工具调用时 `tool_success_rate` 是 `None` 而不是 `0.0`。

- 代码锚点：`engine/observability/health.py`

### 保留策略

三条独立的界：2000 次完成运行 / 90 天 / 512 MB。环境变量可覆盖，**`0` 表示禁用该条**。

- 代码锚点：`engine/observability/index.py:ObservabilityRetentionPolicy`

## 7. MCP

### MCP（Model Context Protocol）

外部工具协议。声明版本 `2025-11-25`，接受 4 个版本。

### 两种传输

`StdioMCPTransport`（子进程逐行 JSON-RPC）、`StreamableHTTPMCPTransport`（HTTP + SSE）。

### 四道边界

单消息 1 MB / 整流 64 MB / 请求墙钟 600 秒 / 工具列表 100 页。

**墙钟是必需的第四道**：前三道拦不住"涓流"，因为涓流恰恰不花字节。

- 详见：[12 · MCP 集成](../subsystems/26-MCP集成.md) §4

### `framing_broken`

stdio 传输超限后的**永久报废**标记。逐行 JSON-RPC 没有帧长度前缀，中途放弃读取会让流永久失同步。

## 10.1 这套文档怎么用

十四篇不是让人从头读到尾的。三种典型的使用方式：

**① 带着问题查。** 从本文 §11.4 的按任务索引进去，或者从 §0 和 §10.3 的混淆对照进去。每个条目都带代码锚点，可以直接跳到源码核对。

**② 接手某个子系统时通读一篇。** 每篇的结构是固定的：全景 → 核心机制逐节展开 → 参数速查 → 设计取舍 → 测试映射 → 改动前的自检问题。**先读全景和自检问题，再回头看中间**——自检问题会告诉你哪些节是必读的。

**③ 改动之前查约束。** 各篇末尾都有"改 X 之前先问几个问题"，那是这一层最容易踩的坑的浓缩版。配合本文 §11.4 的"改东西"表使用。

三条通用建议：

- **代码是准的，文档可能过期。** 每处论断都给了代码锚点，冲突时以代码为准，并**回来修文档**（[01](../guide/01-产品定位.md) 记录了旧 `docs/` 的四处漂移，就是没人回来修的结果）。
- **数字要自己核一遍。** §10.4 的十二个数字每个都带核实方式，一条命令的事。本套文档自己就在写作过程中抓到过两个数字错误。
- **测试名比文档更精确。** 各篇的"测试锁住了什么"一节把测试名和章节对应起来了。想确认某条行为是否真的成立，读那个测试比读文档可靠。

### 这套文档不覆盖什么

三类内容刻意没写，避免读者白找：

**① API 的逐字段参考。** 34 个端点在 [09](../layers/43-Server.md) §2 有全表，但请求/响应的每个字段没有逐条列出——那些在 `server/app/schemas/` 里，且会随版本变。文档写的是**端点的语义和约束**，不是 schema 快照。

**② 逐行代码讲解。** 每篇引用的都是**带设计决策的片段**（通常是注释解释了"为什么"的那些），不是完整实现。想看完整逻辑请直接读源码——文档给的是路标，不是替代品。

**③ 未来规划。** 只记录**已经存在的东西**和**明确否决的东西**（§10.2）。没有 roadmap，因为一份过期的计划比没有计划更容易误导人。

## 10.2 六个被明确否决的做法

文档里记录"没做什么"和记录"做了什么"同样重要——否则每隔一段时间就会有人重新提出同一个方案。以下六项都是**试过或考虑过之后被否决的**，理由记在案。

### LLM 意图分类兜底

**做过，删了。** 早期版本在关键词没命中时调一次 LLM 判断意图。

否决理由有两条：让每一轮普通对话都多一次 LLM 调用（明显变慢）；**会启动一个用户根本没要求的多步工作流**（[02](../guide/02-快速上手.md) §14.1）。

现在的规则是管线需要一个明确声明的高置信度意图——想走 TDD 就说"用 tdd"。**可预测比智能重要。**

### 记忆的查询时检索

**从未实现，且明确不做。** 没有 embedding、没有 FTS 索引、没有 episodes。

两份视图整份注入 prompt，字符上限分别是 4 000 和 10 000（[05](../subsystems/21-记忆系统.md) §3）。代价是记不了太多，收益是**每一轮 prompt 里有什么完全可预测**——你可以直接打开那两个文件看 Agent 记得什么。

早期设计里有 `recent.md`、episodes、降级写入三项，都已否决，不要照旧版方案改。

### 降级写入记忆

**明确否决。** 编译失败时不写一份"尽力而为"的草稿。

理由是记忆有自我强化特性：一份降级的草稿会成为下一轮编译的**可信基线**，一轮轮把记忆稀释掉，且没有任何一步会报错（[05](../subsystems/21-记忆系统.md) §15.1 ①）。

### 从模型名推断能力

**明确否决。** 模型名是任意字符串，中转站可以叫它任何名字。

所以 `thinking` 和 `prefix_cache_key` 默认关闭，必须显式声明；`context_window` 拿不到就用默认值并标记 `*_declared=False`（[07](../subsystems/25-LLM集成.md) §17.2 ③）。

### 让工具自己声明"我不需要审批"

**明确否决。** `TOOL_META` 里的 `approval_policy` 是**输入**不是**结论**——最终由 `engine/safety/` 判定。

理由是工具可以由用户提供（甚至从网上抄来）。如果内容层能声明自己安全，整个安全模型就崩了（[03](10-系统架构.md) §12.3 ③）。

### 知识注入（domain knowledge injection）

**从未实现，记录在案以免被误认为已有功能。** `agent_profiles.knowledge` 是一个 `list[str]` 列，但 **prompt 装配器根本不读它**。

`CLAUDE.md` 的 §10 专门记录了这一条，因为早期文档描述过这个机制，容易让人以为它存在。

## 10.3 五组"名字很像但不是一回事"

§0 列了九组最容易搞混的。这里是另外五组——它们的名字更像，混淆也更隐蔽。

### `approval_required` vs `allowed=False`

`GuardResult` 的两个不同结论：

| | 含义 | 用户看到 |
|---|---|---|
| `approval_required=True` | **检查都过了**，只差用户点头 | 一个审批提示 |
| `allowed=False` | **这个操作本身不行** | 一条拒绝理由 |

混为一谈的后果是用户被问一堆根本不该发生的操作——而问得越多，他越倾向于无脑批准（[06](../subsystems/23-工具与安全.md) §3.1）。

### `boundary_block` vs 敏感文件拦截

两种限制**正交**：

| | 管什么 | 会话白名单能放宽吗 |
|---|---|---|
| `boundary_block` | 路径超出工作目录 | **能** |
| 敏感文件拦截 | 这个文件本身不该碰 | **不能** |

把它们合成一个开关是很自然的实现失误——都是"允许访问"。两个测试专门守这条（[08](../layers/42-Agents.md) §10.1.5）。

### `DONE` vs `RUN_FINISHED`

两个都是"结束"，粒度不同：

| | 什么结束了 | 消费方该做什么 |
|---|---|---|
| `DONE` | **一段执行**（管线的一个节点） | 停止追加文本 |
| `RUN_FINISHED` | **整个 run** | 收起进度指示、写摘要、跑 StopHook |

一次 run 里可以有多个 `DONE`，但只有一个 `RUN_FINISHED`（[03](10-系统架构.md) §3.3 ③）。

### 工具超时 vs 审批超时

同一个 `TOOL_CALL_RESULT` 事件里，"超时"有两种完全不同的含义：

| | 发生了什么 | 字段 | 算事故吗 |
|---|---|---|---|
| 工具超时 | 工具跑太久没返回 | `timed_out=True` / `error_kind="timeout"` | **算** |
| 审批超时 | **用户 300 秒没点批准** | `reason="Approval timed out"`，**不设** `timed_out` | **不算** |

按 `reason` 文本判断会把两者都命中——于是"用户离开键盘"被记成"工具故障"，拉低健康度、触发诊断、生成一条无用建议（[10](../subsystems/27-可观测性.md) §5.2.3）。

### `local-estimate` vs provider 上报用量

| | 来源 | 能当账单核对吗 |
|---|---|---|
| provider 上报 | 响应里的 usage 字段 | 能 |
| `local-estimate` | **没有用量数据时的本地估算** | **不能** |

两者在统计里分开标记。缺字段时**填零而不估算**（[07](../subsystems/25-LLM集成.md) §18.3）——因为一个估算出来的数字混进成本统计后，使用者无法分辨哪些是真实上报的。

## 10.5 补充术语表

以下条目在各篇正文里出现过，按子系统归类。

### `PromptLayer` / `trim_priority`

prompt 的一层。16 层各带五个正交元数据维度（`source` / `authority` / `trust` / `scope` / `load_reason`）加一个 `trim_priority`。

`trim_priority` 为 `None` 表示**永不裁剪**——十层如此。有值的六层按数字升序裁掉：`output_style`(10) → `durable_context`(19) → `skills`(30) → `tool_definitions`(35) → `toolbox_policy`(40) → `style`(50)。

规律：**身份、指令、治理、事实一律不裁，能力目录和表达偏好可裁**。详见 [04](../subsystems/20-Agent-Loop.md) §2.3。

### 稳定前缀（stable prefix）

prompt 里从第一层开始**连续的、跨请求不变的**那一段，用于 provider 的前缀缓存。

关键是"连续"：provider 按**字节前缀**匹配，第一个易变层就终结了前缀。当前边界在第 10 层与第 11 层之间（`eval_guidance` 的 `load_reason` 是 `EVAL_SENSITIVE`，属易变）。往前十层里插入任何内容都会让缓存边界前移。详见 [04](../subsystems/20-Agent-Loop.md) §2.4。

### `RiskTier`

四档风险：`ROUTINE` / `ELEVATED` / `HIGH` / `CRITICAL`。

决定两件事：要不要审批、能不能进会话白名单。**HIGH 与 CRITICAL 永不缓存**——即使用户上一次批准过同样的操作，下一次仍然要问。

风险等级在守卫层算出后**随审批请求一起传递**，消费方不重新推导（[06](../subsystems/23-工具与安全.md) §6.4）。

### `ApprovalScope`

用户批准的那个**具体能力**，而不是一类操作。批准"运行这条命令"不等于"从此可以随便运行命令"。

`ToolRegistry` 在执行前会**再检查一遍** scope 是否匹配——审批和执行之间不能有偷换。

### `boundary_block`

`GuardResult` 的一个字段，表示"唯一的问题是工作目录边界"。

它和 `allowed=False` 的区别在于**可放宽性**：会话级白名单可以扩展边界，但**不能解除敏感文件保护**（[08](../layers/42-Agents.md) §10.1.5 有对应测试）。两种限制正交。

### `LLMPort` / `ProviderAdapter`

两个 `Protocol`，分别面向执行层和 provider。

字段分布就是分层依据：`stream` 和 `limits` 只在 `LLMPort` 侧（执行层要选、要算预算），`max_output_tokens` 在 adapter 侧可以是 `None`（表示"我不知道"）。入参形状也不同——`LLMPort` 收裸参数，`ProviderAdapter` 收 `LLMRequest` 值对象。详见 [07](../subsystems/25-LLM集成.md) §2.4。

### `*_declared` 布尔

`context_window_declared` / `max_output_tokens_declared`。

标记这个容量数字**是 provider 声明的还是引擎的兜底默认值**。依赖它做精确预算的代码据此决定要不要留余量。回放时一律为 `False`（录制不包含容量事实）。

### `prefix_cache_key`

一个声明式能力（`ProviderCapabilities.prefix_cache_key`）加一个请求参数。

不是所有 provider 都支持，所以是**能力**而非假设。Anthropic 的缓存断点需要修改消息结构，因此有一条约束：**不能改调用方传入的消息列表**（`anthropic_cache_breakpoint_does_not_mutate_caller_history` 测试）。

### `_STATE_CHANGING_SHELL_KEY`

FactGate 给 shell 命令的分类结果在上下文里的键名。

分类一次，后续复用。判定依据是三份只读名单（26 个命令 + 9 个 git 子命令 + 3 个结构化工具的读动作），**白名单之外一律算改变状态**（[06](../subsystems/23-工具与安全.md) §7.1）。

### 借用（borrowed）客户端

MCP 会话池的所有权语义：运行时拿到的客户端是**借来的**，**绝不能关闭**。关闭权只属于会话删除和进程退出两个时刻。

违反的后果很具体：两个并发请求里跑得快的那个结束时关掉连接，跑得慢的下一次调用撞上死连接——而配置指纹没变，池还会继续把这个死客户端借出去（[12](../subsystems/26-MCP集成.md) §8）。

### `legacy_linked`

哈希链的一个字段，声明"我之前有一段未链接的老记录"。

必须**显式声明**而不能从"没有 hash 字段"推断——后者可伪造，会让任意前缀被删除后仍能通过校验。这个字段本身参与 `record_hash` 计算，所以攻击者无法事后添加（[13](../layers/40-Common.md) §6.7）。

### 锚点（anchor）

`.head` 文件，记录封存时刻的链头（`seq` + `hash`）。

哈希链本身能证明"这串记录内部自洽"，但证明不了"这串记录就是当初写下的那串"——整体回滚到一个更早的合法版本，链依然自洽。**只有外部锚点能识破回滚**（[13](../layers/40-Common.md) §6.6）。

对应的代价是：合法的续写必须先 `reopen()` 清掉陈旧锚点，否则会被报成篡改。

### `_observed_size`

`HashChainLog` 用来检测"是否有别的进程追加过"的字段——记录自己上次写完时的文件大小。

不相等就重扫尾部恢复状态。这防的是**并发写者让链分叉**：两个实例各自缓存 seq，都从同一个 prev_hash 写，校验时报 sequence gap——**没人篡改却报了篡改**（[13](../layers/40-Common.md) §6.10 ①）。

### 交替 flush

Shell 里两个批处理器（普通文本 / 试探性文本）保证顺序的手法：**换一种文本之前，先把另一种攒着的吐出去**。

不这么做的话，两个 40ms 计时器各自到期，进 store 的顺序会和到达顺序脱钩，用户会看到试探性内容插在一段普通文本中间（[11](../layers/44-Shell.md) §5.7）。

### OSC 注入

终端转义序列攻击的一类。四个具体的：

| 序列 | 危害 |
|---|---|
| **OSC 52** | 写系统剪贴板，**在 kitty / wezterm / alacritty 默认允许** |
| OSC 7 | 伪造终端上报的 cwd |
| OSC 0 | 伪造窗口标题 |
| OSC 8 | 把钓鱼目标藏在无害的链接文字后 |

Ink 碰巧吸收 CSI 序列，但 **OSC 会原封不动到达终端**，所以必须在解码边界主动净化（[11](../layers/44-Shell.md) §5.10）。

### trojan source（bidi override）

用双向格式字符（`U+202A`–`U+202E`、`U+2066`–`U+2069`）让**文本的显示顺序和字节顺序不一致**。

它们是普通可打印码点，控制字符过滤放行。危险点很具体：**审批提示要渲染模型给的工具参数**，一个 RLO 就能让用户读到的命令和他批准的命令不是一回事（[11](../layers/44-Shell.md) §5.11 ③）。

## 11. 反复出现的设计模式

这套代码库里有若干模式在多个子系统独立出现，值得单独列出来。

| 模式 | 出现处 |
|---|---|
| **两端各留一半 + 显式标注中间省略** | 门禁输入 `_bounded_gate_output`、记忆 `_truncate_source`、宿主输出 `host.py` |
| **区分"没数据"与"值为零"** | `usage_reported`、`*_declared`、`tool_success_rate=None` |
| **`bool` 是 `int` 子类，必须显式排除** | `usage.py._number()`、`dream.py._load_dream_cleanup()`、`catalog.py` 的 `priority` |
| **未知字段一律报错** | 身份 YAML、技能设置 YAML |
| **运行时宽容，启动时严格** | 技能缺失降级 + `validate_execution_assets()` |
| **环境变量宽容，代码构造严格** | `ObservabilityRetentionPolicy` |
| **fail-closed** | 工具白名单、路径根发现、记忆守卫、checkpoint 所有权判定 |
| **正则边界断言是承重的** | 路由 `_keyword_hit` 的 ASCII lookaround、记忆锚点的 `\b`、trace 密钥的前置边界 |
| **进程组信号而非单进程** | Shell 拉起 uvicorn、宿主命令执行 |
| **必须手工同步的多份副本** | 凭据清单（3 处）、token 键白名单（2 处）、私钥正则（2 处） |

### 11.1 六个跨子系统的判断原则

上表是"手法"，这一节是"判断标准"——它们在不同子系统被独立总结出来，措辞不同但内核一致。

**① 结构化字段可信，自由文本不可信。**

| 出现处 | 具体表现 |
|---|---|
| [07](../subsystems/25-LLM集成.md) §15.1 ⑤ | 重试分类只看 `type`/`code`/`status`，错误消息一律不进异常 |
| [10](../subsystems/27-可观测性.md) §5.2.3 | `is_timeout` 用 `timed_out`/`error_kind` 区分工具超时与审批超时 |
| [10](../subsystems/27-可观测性.md) §5.2.4 | `_failure_details` 只认紧邻终态的固定通知，不解析任意模型输出 |
| **反例** | [05](../subsystems/21-记忆系统.md) §9.5.1 的退避判据**允许**按文本匹配——因为那些文本是本模块自己产生的，且判错只是多等一会儿 |

判据是**代价**：文本判错会导致凭据泄漏或重试风暴时，绝不用文本；判错只影响时机时，可以用。

**② 假阳性与假阴性的代价不对称，方向因层而异。**

| 场景 | 倾向 | 理由 |
|---|---|---|
| 密钥检测（[05](../subsystems/21-记忆系统.md) §12.1） | **宁可多删** | 漏一个凭据会长期留在 prompt 里 |
| 注入检测（[05](../subsystems/21-记忆系统.md) §12.2） | **宁可少删** | 误删的是用户真正需要的项目笔记 |
| 敏感文件拦截（[08](../layers/42-Agents.md) §10.1.2） | 拦，但**放行 `.env.example`** | 模板是给人看的文档 |
| 普通读审批（[06](../subsystems/23-工具与安全.md) §11.1.2） | **不拦** | 动不动弹审批会让用户养成盲批习惯 |

同一个文件里两套模式松紧相反是正常的（`_files.py` 的密钥宽、注入严），**关键是每一条都要想清楚误伤什么**。

**③ 显式声明胜过隐式推断。**

| 出现处 | 被否决的推断 |
|---|---|
| [13](../layers/40-Common.md) §6.7 | "没有 hash 字段就是 legacy 记录"——可伪造，导致前缀删除 |
| [13](../layers/40-Common.md) §2.7 | "有 `agents/` 目录就是项目根"——会误认别的项目 |
| [08](../layers/42-Agents.md) §4.1 | "从模型名推断能力"——模型名是任意字符串 |
| [12](../subsystems/26-MCP集成.md) §6.3 | "从 server 自述推断工具风险"——自述不可信 |

**从缺失推断意图永远可伪造**，从相似推断身份永远会误判。

**④ 副作用一旦对外可见就不能回滚。**

| 出现处 | 分界线 |
|---|---|
| [07](../subsystems/25-LLM集成.md) §18.2 | 第一个内容 delta 发出后不再重试 |
| [07](../subsystems/25-LLM集成.md) §12.3 | 录制在流结束后一次性写，不逐事件追加 |
| [09](../layers/43-Server.md) §4.7 | 校验全部在 SSE 流打开之前 |
| [11](../layers/44-Shell.md) §5.7 | 中断时 `discard()` 缓冲内容且不 emit |

判断标准是"**外部是否已经观察到**"，不是"内部状态是否干净"。

**⑤ 读路径必须容忍任何版本写下的数据。**

| 出现处 | 手法 |
|---|---|
| [10](../subsystems/27-可观测性.md) §6.6 | 四处 `.get(key, default)`，未知类别不抛 `KeyError` |
| [10](../subsystems/27-可观测性.md) §10.4 | `except ValueError: continue` 跳过不认识的事件类型 |
| [03](10-系统架构.md) §3.4 | 事件类型字符串**只增不改** |
| [12](../subsystems/26-MCP集成.md) §12.2 | `load_recording` 跳过畸形行而非整份报废 |

前提是 trace 和录制会长期保存，**今天的代码要能读懂上个月写下的数据**。

**⑥ 昂贵的检查要有便宜的前置判断。**

| 出现处 | 快路径 |
|---|---|
| [13](../layers/40-Common.md) §2.5 | manifest 先比 mtime+size，不同才算 SHA-256 |
| [13](../layers/40-Common.md) §6.10 ① | 先比文件大小，变了才重扫尾部 |
| [13](../layers/40-Common.md) §4.7 | 连接探活用 `SELECT 1` 而非重建 |
| [06](../subsystems/23-工具与安全.md) §3.3 ② | 硬链接检查先看 `st_nlink < 2` 直接跳过 |

**为罕见情况付出的代价必须小到常见路径感觉不到**——否则安全措施迟早会以性能为由被删掉。

### 11.2 五个"看起来重复但必须重复"的地方

DRY 是默认原则，但这套代码里有五处刻意的重复，各有理由。改动时要认出它们，不要"顺手统一"。

| 重复的东西 | 几处 | 为什么不能合并 |
|---|---|---|
| 凭据配置文件名 | 3 | 沙箱不能 import 安全层，`agents/` 不能 import 引擎（[06](../subsystems/23-工具与安全.md) §3.4） |
| SSH 私钥正则 | 2 | 同上，且一份要写成 POSIX ERE 供 macOS `regcomp` 编译（[06](../subsystems/23-工具与安全.md) §9.3） |
| 子进程环境白名单 | 3 | shell / MCP / git 三处各自构造，同样受层边界限制 |
| 路径推导 | 多处 | `agents/` 拿不到 `common/paths.py` 的常量（[03](10-系统架构.md) §1.2） |
| "只有拿到成功证据才能报告完成" | 3 | 人格文件 + 两条管线的 `instructions`——**刻意加固**，因为这是最严重的失效模式（[08](../layers/42-Agents.md) §11.1 ④） |

前四处是**架构边界的代价**，第五处是**刻意的冗余**。区别在于：前四处如果哪天能安全共享就应该共享，第五处则应该保持重复。

已知的漂移记录有两次，方向相反（[03](10-系统架构.md) §10.3）——这说明问题不在某个模块写得不好，而在结构本身。缓解手段是三层：源码注释写明"Change all three together"、各处测试分别覆盖、本文档把它们列在一起。

### 11.3 三条只在这个项目成立的约定

上面的模式在多数项目里都适用。这三条是 Agent-Smith 特有的，理解它们才能读懂很多设计决策。

**① 可观测性失败不能让运行失败。** 出现在 [10](../subsystems/27-可观测性.md) §10.5、[04](../subsystems/20-Agent-Loop.md) §7.1.7、[09](../layers/43-Server.md) §9.2。取舍方向明确：**任务成功 > 记录完整**。磁盘满了、权限不对，这些是运维问题，不该让用户的任务跑不了。

代价是可能丢观测数据，缓解是崩溃恢复能从 trace 重建（[10](../subsystems/27-可观测性.md) §10.1）。

**② 观察者不能改被观察的东西。** 诊断"proposes changes but never applies them"、建议对象"never mutates runtime configuration"、投影通过依赖注入而非 import 拿到（[10](../subsystems/27-可观测性.md) §14.1 ⑥）。

这既是层边界（避免反向依赖），也是信任边界：**一个能自动改配置的诊断系统，一旦判断错就会自己把问题放大**。

**③ 记忆的错误会自我强化。** 这一条解释了为什么记忆的防御强度和它的代码量不成比例（[05](../subsystems/21-记忆系统.md) §15.1）。别的子系统里一次错误就是一次错误；而记忆的输出是它自己下一轮的输入——一条被错误写入的结论会参与下一次编译，可能被"确认"、被扩写、被当成既有事实引用，几轮之后已无法分辨它最初怎么来的。

所以入口处有四层把关（三道确定性守卫 + 一道 LLM 评审），只为让一件事成立：**写进去的每一句话，都能回溯到一条真实发生过的证据**。

### 11.5 三个词的准确用法

最后三个词值得单独说，因为它们在这个项目里的含义比通用含义窄。

**"Agent"** 在这里**只指 Smith 这一个运行实体**，不是"一个 AI 程序"的泛称。所以"加一个 Agent"这句话在这个项目里没有意义——你能加的是身份、技能、工具。产品语言禁令（不说 sub-agent / employee / hire）就是为了守住这个用法。

**"Skill"** 指的是**一份 Markdown 写的工作方法**，不是"一项能力"。能力是工具（Tool）。一个技能可以完全不调用任何工具（比如 `teach`），一个工具也不属于任何技能。两者正交。

**"Memory"** 指的是**两份被编译出来的渲染视图**，不是"Agent 记得的一切"。会话内的上下文不叫记忆，`recent.jsonl` 里的证据也不叫记忆——前者是上下文，后者是候选证据。只有过了三道守卫和一道评审、写进那两个文件的，才是记忆。

三个词的共同点：**它们都比日常用法窄**。用宽了会让讨论失去精度——"这个 Agent 记住了吗"这句话，在准确用法下要拆成"Smith 的哪份视图里有这条"，而后者才是能被验证的问题。
