# 09 · 外部架构模式对比

> **文档状态：决策输入，非当前实现规范。** 产品版本、工具数量和外部系统行为会随时间变化；涉及 Smith 的现状时以[系统架构](02-系统架构.md)和源码为准。

## 本文目的

本页不再维护一张容易过期的“谁有多少工具/谁支持什么”的功能排行榜，而记录评估外部 Agent 设计时应比较的架构维度。详细原始调研保留在[`reference/`](reference/)与[`research/`](research/)。

## 对比维度

| 维度 | Smith 当前选择 | 评估外部方案时的问题 |
| --- | --- | --- |
| 执行模型 | 单 Agent；按 identity route 选择 ReAct 或顺序 skill pipeline | 是否需要 planner/worker 分工？失败、重试与输出提交如何收敛？ |
| 工具治理 | 本地 provider 与 MCP 工具进入同一 registry，统一 policy/guard/approval | 外接工具能否绕开权限、审计或输出限制？ |
| 记忆 | 受证据约束的 context/recent/durable 视图，按需召回 | 原始对话、摘要、向量索引各自承担什么，谁有写入权？ |
| 长任务 | Run 状态、checkpoint、SSE trace 与 resume | 断线、崩溃、重复提交和取消时是否能恢复且不重复副作用？ |
| UI | Ink Shell 消费事件流 | UI 是否把显示状态与执行事实混在一起？流式结构何时才可固化？ |
| 扩展 | identity、pipeline、SKILL.md、MCP client | 新能力是否能继承安全、run ownership 与测试契约？ |

## 对 Smith 已确认的借鉴原则

1. **单条执行链先完整，再引入多 Agent。** 子 Agent 不是多一次模型调用；还需要资源所有权、上下文隔离、并发写入、审批传播、结果汇总和可观测性。
2. **工具必须是受治理 API。** Tool schema、registry、policy、guard、approval 与 ledger 的边界不可由 skill/插件绕过。
3. **记忆不是聊天备份。** 长期写入需要证据、冲突策略、审核和用户可控的遗忘；当前实现已把这部分独立为 Memory Policy。
4. **可恢复性要进入运行时。** 以终端输出或“done”文本判断任务完成不可接受；Run 状态和事件终态需持久化。
5. **领域化优先使用声明式档案。** 一个 identity + allowlist + pipeline 足以表达很多场景，无需立即创建独立 Agent。

## 结论与边界

当前最值得维护的是单 Agent 的正确性：安全审批、工具结果、pipeline gate、流式终态、恢复、观测和记忆准入。插件市场、团队协作、子 Agent、面向用户的文档 RAG 与强制 worktree 是候选演进项，不是本版本能力——memory 内部的 topic 级向量召回已落地，基础 worktree 工具（`git_ops` 的 `worktree_create`/`worktree_remove`）已存在，未实现的是面向用户的知识库和强制 worktree 工作流（见[路线图](11-开发路线图与待办.md)）。

对某个外部项目的具体观察请在 `research/` 新建带日期和来源的文档；做出产品决定时新增 ADR，并把已实现的结果更新到当前实现文档。
