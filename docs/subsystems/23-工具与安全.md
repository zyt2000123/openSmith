# Agent-Smith 工具与安全体系 — 能力、边界与审批

> 本文面向需要新增工具、调整权限或审计 Agent-Smith 行为的开发者，说明一个工具如何被注册、一次调用要过几道关、什么情况会弹审批、沙箱挡住了什么、以及全过程留下了哪些不可篡改的痕迹。所有清单与常量取自 `agents/tools/`、`engine/tool/`、`engine/safety/`、`engine/sandbox/` 代码。

---

## 一、一句话结论

工具系统的核心不是"有多少工具"，而是**一次调用要串行通过几道彼此独立、失败方向一致的关卡**：

```
模型提出调用
   ↓
① 可见性        不在本次可见集合 → 拒（节点作用域 / 身份白名单 / 配置开关）
   ↓
② ToolPolicy    硬守卫 + 事实门禁，第一个拦截者获胜
   ↓
③ 审批          需要用户点头的，挂起等 broker
   ↓
④ PreToolHook   可插拔阻断（配置保护等）
   ↓
⑤ 幂等账本      同一逻辑副作用只发生一次
   ↓
⑥ 执行环境      host 或 macOS Seatbelt 沙箱
   ↓
⑦ PostToolHook  只能告警，不能回滚
   ↓
⑧ 截断 + 哈希    输出限长，结果哈希绑定证据
```

每一关**独立失败关闭**。删掉任何一关，其余关卡的语义不变。

`sub_agent` 的元数据有两处值得解释（`agents/tools/sub_agent.py:63`）：它的 `side_effect` 是 `write` 而不是 `none`，因为**子 Agent 自己可能持有可写工具**——外层调用不能按只读记账；它的 `concurrency` 是 `serial`，因为并发宽度活在这一次调用**内部**（`max_parallel`），而不是跨调用。能力矩阵与不变量见 [24 · 子 Agent 委派系统](24-子Agent委派.md)。

三档 `approval_policy` 的语义：

| 值 | 含义 |
|---|---|
| `never` | 不因为工具本身要审批（路径/规则命中仍可能触发） |
| `policy` | 由守卫按参数决定（越界、敏感路径、危险规则） |
| `always` | 每次都要审批。目前只有 `shell` |

### ToolDefinition 的安全元数据

权限不是靠维护一份工具名单，而是靠工具**自己声明**：

| 字段 | 用途 |
|---|---|
| `path_args` / `list_path_args` | 哪些参数是路径，守卫据此提取并检查 |
| `is_write_tool` | 路径检查按写权限还是读权限判 |
| `opaque_command` | 参数是不透明命令串，需要额外做 shell 路径提取（只有 `shell`） |
| `network_access` | 打开网络连接，即使看起来只读也计入风险 |
| `permission_level` | read / write / execute / destructive |
| `approval_policy` | never / policy / always |
| `read_actions` | 结构化工具里哪些 action 算只读（如 `git_ops` 的 `status`/`diff`/`discover`） |
| `side_effect` | none / write / external / destructive，决定是否进幂等账本 |
| `idempotent` | 重跑是否到达同一终态，决定不确定态能否重试 |
| `concurrency` | safe / serial |
| `execution_environment` | host / sandbox / either |
| `hidden` | 注册但默认不暴露给模型 |
| `timeout_seconds` / `retryable` | 执行契约 |

## 三、路径规范化：让守卫和 provider 看同一个文件

`ToolRegistry.normalize_call` 在**策略检查之前**跑，把声明路径相对工作目录解析成绝对路径。

关键点是它同时保留两个视图：

| 视图 | 值 | 用途 |
|---|---|---|
| `arguments[arg]` | `Path.resolve()` 后的真实路径 | provider 实际打开的文件 |
| `declared_paths[arg]` | `os.path.abspath()`，**不跟随符号链接** | 守卫的目录名规则匹配 |

为什么要两个：`resolve()` 会抹掉符号链接的**名字**——一个指向别处的 `.git` 符号链接解析后，路径里就没有 `.git` 这个组件了，而 `FileGuard` 的规则正是按组件名写的。两个视图一起检查，两种攻击面都覆盖。

`setdefault` 保证幂等：`execute` 会再规范化一次作为兜底，如果从已解析参数重新推导声明视图，会把它塌回解析路径——**静默让第二次（执行时）检查比第一次弱**。

还有一条防御性拒绝：声明为标量的路径参数如果收到 list 或 dict，直接拒绝而不是 `str()` 成一个假路径。守卫检查那个假路径、provider 读到真值，是典型的 check/execute 分歧。

## 四、ToolPolicy：策略网关

`engine/safety/tool_policy.py`。它是一条 `PolicyChecker` 链，**第一个拦截者获胜**，但有一个刻意的例外。

```
ToolPolicy.evaluate(call)
   ├─ _ToolGuardAdapter   硬安全边界（不可绕过）
   └─ _FactGateAdapter    事实门禁（只挑战，可重试）
```

### 例外：事实门禁优先于审批

```python
if decision.approval_required:
    deferred_approval = ...   # 记下来，继续问下一个 checker
    continue
```

理由写在代码里：**第一次尝试必须先把事实建立起来；只有重试才允许停下来等审批。** 反过来的话，用户会先看到一个审批弹窗，批准之后模型才被告知"你还没调查过"——顺序反了。

### 三种不通过

| 判定 | `observation` 前缀 | 消耗的预算 |
|---|---|---|
| 挑战（challenged） | `[PREFLIGHT]` | preflight 预算 |
| 阻断（blocked） | `[BLOCKED]` | 失败恢复预算 |
| 需审批 | 挂起等 broker | 不消耗，等用户 |

## 五、ToolGuard：不可绕过的硬边界

`engine/safety/tool_guard.py`（1365 行，全系统第二大文件）。检查顺序本身就是设计：

```
① 运行时凭据检查
   命令提到 Agent 运行时凭据文件 → CRITICAL 拒绝（不可委派）
        ↓
② 危险命令规则（31 条，agents/safety/dangerous_commands.json）
   命中 → DESTRUCTIVE + CRITICAL + 强制高风险审批
        ↓
③ 文件路径检查（FileGuard）
   越界 / 敏感文件 / 符号链接逃逸 / 硬链接同 inode
        ↓
④ 一般审批判定
   approval_policy + 风险分级
```

第 ③ 步必须排在第 ④ 步之前，理由代码里写得很清楚：否则 `read_file /etc/shadow` 会被呈现为一次普通的"目录边界审批"，而不是它实际是的高风险凭据/系统文件访问。

### 危险命令规则的九类

| 类别 | 规则数 | 示例 ID |
|---|---|---|
| 命令注入 | 4 | `cmd-inj-001` 管道进 shell 解释器 |
| 资源滥用 | 3 | `res-abuse-001` fork 炸弹 |
| 动态代码执行 | 4 | `code-exec-001` Python `eval`/`exec` |
| 网络滥用 | 3 | `net-abuse-002` 反弹 shell |
| 敏感文件 | 4 | `sens-file-002` SSH 密钥 |
| 提权 | 3 | `priv-esc-001` sudo/su |
| 规避检测 | 3 | `sh-evade-001` base64 解码进 shell |
| 破坏性操作 | 4 | `destruct-001` 递归强制删除 |
| **平台自保护** | 3 | `platform-protect-001~003` |

最后三条是 Agent-Smith 特有的：**禁止模型往自己的运行时目录装包、改文件、重定向输出**。它们锚定在 `common/paths.py` 定义的数据根上——单一事实来源，不是散落的字符串常量。

规则支持 `tools`（限定作用工具）、`patterns` / `pattern`、`excludePatterns`。规则文件在加载时校验结构，**改坏了要在启动时大声失败**，而不是让每一次 agent run 变成一个不透明的错误。

### FileGuard 的四道

| 检查 | 拦的是 |
|---|---|
| 工作目录边界 | 越界读写（可由会话白名单扩展） |
| 敏感文件名/扩展名 | `.pem` `.key` `.p12` `.pfx`、`id_rsa` 家族、`.npmrc` `.pypirc` `.netrc` `.git-credentials`、`.git/config` 与 `credentials` |
| 符号链接 | 解析视图与声明视图**双检查** |
| 硬链接 | `_shares_inode_with_protected_file` —— 同 inode 的另一个名字不能绕过路径规则；扫描跳过 `objects`、`node_modules`、`.venv`、`__pycache__` |

另有一条**非委派写根**（`set_non_delegable_write_roots`）：`agents/tools/` 目录本身。模型可以读工具源码，不能改——改了下一次 run 就带着它跑。

## 六、风险分级与审批

### RiskTier

`engine/safety/risk.py`。四级有序，`RiskTier.max()` 取策略链上最严的一档。

| 等级 | 含义 | 能否缓存到会话白名单 |
|---|---|---|
| `ROUTINE` | 只读 / 无副作用，直接执行 | 不涉及 |
| `ELEVATED` | 普通写、越界访问，问一次 | ✅ 可以 |
| `HIGH` | 敏感路径、网络、运行时状态 | ❌ 每次都问 |
| `CRITICAL` | 命中危险规则或 destructive 级 | ❌ 每次都问 |

这个分级不是装饰。它的**唯一职责**就是路由行为：registry 只对最低审批档缓存会话白名单，`HIGH`/`CRITICAL` 必须每次重新授权。

`execute` 级别**故意不自动升为 HIGH**——没有声明权限级别的工具默认就是 EXECUTE，光凭级别不足以判定风险。

### 审批 scope

审批批的不是"这个工具"，是**一次具体的能力请求**（`ApprovalScope`）：

| 工厂方法 | 含义 |
|---|---|
| `host_command(command)` | 一条宿主机命令 |
| `path(...)` | 一个路径上的一类操作 |
| `network(target)` | 一个网络目标 |
| `operation(...)` | 一次结构化操作（如某个 `git_ops` action） |

scope 会带到 broker、带回 registry 再检一遍，还会带进 Seatbelt 环境（`with_approval_scope`）。

### 审批流

```
守卫判定 approval_required
        ↓
broker.open(ApprovalRequest)  ── 发 TOOL_CALL_RESULT(approval_required=true, presentation=...)
        ↓                        run 状态转 WAITING_APPROVAL
await broker.wait(...)         默认超时 300 秒
        ↓
   ┌────┴────┐
批准          拒绝 / 超时
   ↓             ↓
带 approval_id   写 [BLOCKED] tool 结果 + tool_blocked_prompt
继续执行         approval_outcome = denied / timed_out
原封不动的那次调用
```

批准之后**继续执行原来挂起的那次调用**，而不是让模型重新构造一次——重构造有产生重复副作用的风险。

参数摘要 `summarize_arguments` 有硬上限（32 项 / 3 层 / 240 字符），并对疑似敏感参数名和疑似密钥值做脱敏。

### 会话白名单

`SessionWhitelist` 记三类：工具名、路径前缀、精确文件。`/init` 这类明确动作会用 `allow_project_instruction_path` 只白名单化 `<project>/.smith/SMITH.md` 这一个规范文件——不是整个 `.smith/` 目录。

## 七、事实门禁（Fact Gate）

`engine/safety/fact_gate.py`。它**不是**硬边界，也**不是**可插拔 hook：它按请求装配在 `lifecycle.py` 里，始终生效，**只挑战不阻断**。

作用：一个回合里第一次做状态变更操作时，先要求模型去调查。灵感来自 ECC GateGuard 的 fact-forcing hook（MIT）。

判定"这是不是只读"是它的全部难点：

| 场景 | 判定方式 |
|---|---|
| 普通命令 | 白名单：`cat` `ls` `grep` `rg` `head` `tail` `wc` `diff` `stat` `file` `tree` `df` `du` `which` … |
| git | 子命令白名单：`status` `diff` `log` `show` `blame` `grep` `ls-files` `ls-tree` `rev-parse` |
| sed | 单独判定 —— `-i` 就是写 |
| 结构化工具 | `read_actions` 声明：`git_ops`→`{diff,discover,status}`，`memory_ops`→`{search}`，`skill_manage`→`{get,list,versions}` |
| 复合命令 | 按 `;` `&` `&&` `\|\|` `\|` 切段，任一段不是只读则整条不是；重定向符一律算写 |

可通过环境变量关闭（`_DISABLE_VALUES`：`0` `false` `off` `disabled` `no`）。

## 八、幂等账本

`engine/tool/ledger.py`。只对 `side_effect != "none"` 的工具生效，SQLite 支撑。

问题背景：provider 的 call ID 在**恢复的模型调用**之后会重新生成。光靠 call ID 无法判断"这是同一个副作用的重放"还是"一次新的相同操作"。

解法是语义键 + 出现序号：

```
semantic = sha256({"tool": 名字, "arguments": 参数})   # 规范化 JSON
key      = f"semantic:{semantic}:{第几次出现}"
```

出现序号保留了"故意重复的等价调用"，同时让恢复的 run 能重放对应的那一次。

`begin()` 的几种结果：

| 账本状态 | 动作 |
|---|---|
| 无记录 | 认领，插入 `running` |
| `completed` | **重放**记录的结果，不再执行 |
| `uncertain` + 工具声明 `idempotent` | 允许重新认领 |
| `uncertain` + 非幂等 | 本 run 剩余时间内拒绝 |
| `running` | 有主，绝不抢——即使是幂等工具，抢了会让两次执行重叠 |

## 九、执行环境：macOS Seatbelt

`engine/sandbox/macos_seatbelt.py`。`shell` 声明 `execution_environment: sandbox`，在 macOS 上通过 `/usr/bin/sandbox-exec` 执行。

sandbox 绑定**不替换** host 后端，而是并存。声明 `host` 的工具永远不会被静默重定向进沙箱，反之亦然。

### 未授权宿主访问时的 profile

```lisp
(version 1)
(deny default)
(import "system.sb")
(deny network*)
(allow process*)
(allow file-read*  (subpath (param "WORKSPACE")))
(allow file-write* (subpath (param "WORKSPACE")))
; 然后在工作区内部再挖掉这些：
;   .env / .env.*
;   .ssh .gnupg .aws .kube .agent-smith .docker
;   .config/gh  .config/gcloud
;   Library/Keychains
;   *.pem *.key *.p12 *.pfx
;   id_rsa / id_dsa / id_ecdsa / id_ed25519 家族
;   .git/（除 .gitignore 外全部）
;   .npmrc .pypirc .netrc .git-credentials
```

两个值得注意的实现细节：

1. **`WORKSPACE` 通过 `sandbox-exec -D` 传入，不做字符串插值**，再配 `regex-quote`——把用户可控的路径字符全部挡在 SBPL 语法和正则语言之外；
2. **`.git/` 整个禁读**（`.gitignore` 不匹配 `\.git(/|$)`）：`.git/config` 可能内嵌凭据，object 文件可能含已提交的密钥。显式的 config/credentials 规则保留着，是为了让意图可见，即使已被兜底规则覆盖。

用户批准宿主访问后 profile 放开，但**仍然逐条 deny 运行时凭据路径**，并保留非委派写路径的 deny。

私钥文件名的正则形状只有一份来源（`_PRIVATE_KEY_NAME_PATTERN`），Python 侧检查和 profile 用同一个常量——这两处曾经漂移过一次，而**只有 profile 决定 shell 实际能打开什么**。

宿主执行（`engine/sandbox/host.py`）也有护栏：输出上限 10 KB（保头保尾，中间打 `... (middle truncated) ...`）、超时后按进程组发信号、1 秒宽限期。

## 十、输出治理

`engine/tool/truncation.py`：超过 **2000 行**或 **50 KB** 的工具输出会被截断，完整内容写到 `~/.agent-smith/tool-output/`，返回的预览里带文件路径提示。

`TOOL_CALL_RESULT` 事件里只放 200 字符预览，但同时带一个 `result_hash`：

```python
result_hash = tool_result_hash(
    tool_name=..., call_id=..., arguments=..., content=完整内容, is_error=...
)
```

哈希算的是**完整结果**，只存哈希。这样一条门禁判定可以事后对着"这次调用到底产出了什么"核验，而不需要把原文抄进 trace。

## 十一、审计：哈希链

`AuditLog` 写 `~/.agent-smith/audit.jsonl`，每条记录带 `seq` / `prev_hash` / `hash`（`common/hash_chain.py`）。改写、重排、删除任何一条历史记录都可被 `verify()` 检出。

链头在 `close()` 和进程关闭时锚定到 `<log>.head`，所以"回滚到一个更短但自洽的链"同样能被检出。

三个设计约束：

1. **链是按日志路径进程内共享的**——每请求一个 guard 实例，不代表每实例一份独立的共享 append-only 文件视图；
2. **不按 run 封链**：日志是安装级的，并发 run 会交错写入，run 边界不是链头。在那里写锚点，下一个 run 一 append 就过期，自己就会读成 `anchor mismatch`；
3. **`check(audit=False)`**：registry 在执行前会再跑一次守卫做兜底，不抑制审计的话，审计轨迹里的工具调用数会是实际的两倍。

记录内容经 `_summarize_args` 脱敏，不落原始参数值。

## 十二、可插拔 Hook

| 类型 | 时机 | 阻断 | 内置实现 |
|---|---|---|---|
| `PreToolHook` | 执行前，按 priority 排序 | ✅ | `config-protection` |
| `PostToolHook` | 执行后 | ❌ 只告警 | `console-warn`、`quality-gate`（异步） |
| `StopHook` | 每次响应结束 | ❌ | `cost-tracker` |

加载顺序：`agents/smith/hooks.yaml`（内置）→ `~/.agent-smith/hooks.yaml`（用户）。

`agents/smith/hooks/` 是**架构边界的唯一豁免**：hooks 实现 `engine.execution.hooks` 的 ABC，并可读 `common` 拿数据根。其余 `agents/` 内容（gates、conditions、tools）不 import 任何其他层，由测试强制。

## 十三、MCP 外部工具

`engine/mcp/`。外部 MCP server 的工具会注册进同一个 registry，因此**同样受上面所有关卡约束**。

三条硬性上限值得知道：

| 限制 | 值 | 原因 |
|---|---|---|
| `MAX_TOOL_NAME_LENGTH` | 64 | provider 对工具名长度有限制 |
| stdio StreamReader | 提高到 `MAX_MCP_RESPONSE_BYTES` | asyncio 默认 64 KiB，很多 MCP server 单次响应轻松超过 |
| SSE 流上限 | `64 × MAX_MCP_RESPONSE_BYTES` | 防止流式响应无限增长 |

子进程环境经 `_mcp_subprocess_environment` 过滤；命令与 URL 在日志里经 `_redact_command` / `_redact_url` 脱敏。

## 十四、常见问题

**Q: 加一个新工具要动几个地方？**

一个文件。在 `agents/tools/` 放一个 `.py`，定义 `TOOL_META`（含安全元数据）和 `execute`。守卫、审批、风险分级全部从元数据推导，不需要改 `engine/`。

**Q: 为什么 `shell` 是 `approval_policy: always`？**

因为它的参数是不透明命令串（`opaque_command: true`）。守卫会做 shell 路径提取和危险规则匹配，但静态分析永远不可能穷尽一条命令能做什么。每次都问是唯一诚实的答案。

**Q: 批准过一次的操作，下次还会问吗？**

看风险等级。`ELEVATED` 可以进会话白名单，之后不再问；`HIGH` 和 `CRITICAL` **每次都问**。这条正是 `RiskTier` 存在的意义——它不是用来显示的，是用来路由缓存行为的。

**Q: 事实门禁会不会拖慢每一次编辑？**

一个回合只挑战第一次状态变更操作，`begin_round()` 复位。而且它有独立的预算（20 次），耗尽后不再挑战。可以用环境变量整体关掉。

**Q: 沙箱只在 macOS 上有？**

目前是。`prepare_runtime` 里的 `MacOSSeatbeltEnvironment` 绑定被 `sys.platform == "darwin"` 守着。其他平台上 `shell` 走宿主环境，此时守卫的规则匹配与路径检查是唯一防线（这也是那 31 条规则和非委派写根存在的原因）。相应地，engine 测试里约 59 个 Seatbelt 用例都带 `@pytest.mark.skipif(sys.platform != "darwin")`——在 Linux 上*失败*而不是跳过，说明有用例漏了这个标记。

**Q: 模型能改自己的工具代码吗？**

不能。`agents/tools/` 被登记为非委派写根，同时 Seatbelt profile 里有对应的 `deny file-write*`。两处独立设防：一处是策略层，一处是内核层。

**Q: 怎么证明某次危险操作确实被拦了？**

`~/.agent-smith/audit.jsonl`，带 `rule_id`、`risk`、`level`、`allowed`、`call_id`、`run_id`。哈希链保证记录没被事后修改。配合 run trace 里的 `TOOL_CALL_RESULT`（含 `result_hash`、`approval_id`、`approval_outcome`）可以完整还原一次调用的判定过程。
